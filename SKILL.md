# Money Management UI Design Skill

## Purpose

Use this skill whenever creating, modifying, reviewing, or redesigning the visual interface of the Money Management application.

`DESIGN.md` is the visual source of truth. `CLAUDE.md` remains the source of truth for project architecture, data safety, scope, and coding rules.

This skill exists to prevent generic AI-generated UI patterns and to keep the application's visual language coherent over time.

---

## 1. Before Changing UI

Read:

1. `CLAUDE.md` for project and data rules.
2. `DESIGN.md` for visual rules.
3. Only the CSS/HTML/JS files directly relevant to the requested UI change.

Do not perform a full-project UI audit unless the user explicitly asks for a full redesign.

For a full redesign, first inspect the existing global CSS, main shell, navigation, typography, themes, and representative pages before changing them.

---

## 2. Design From the Existing System

Before creating a new visual component:

1. Search for an existing component with the same role.
2. Reuse its structure/classes where appropriate.
3. Extend the shared CSS system rather than creating isolated styling.
4. Only create a new pattern when the existing pattern cannot express the requested interaction clearly.

Do not duplicate:

- buttons
- inputs
- cards
- modal styles
- navigation patterns
- status styles
- typography rules

without a concrete reason.

---

## 3. Pure Local Visual Implementation

All new visual design must be implemented with:

- HTML
- CSS
- vanilla JavaScript
- local project assets when necessary

Do not add:

- Tailwind
- Bootstrap
- Material UI
- component libraries
- external CSS
- external icon libraries
- remote fonts
- CDN visual assets
- stock images
- online UI kits

Do not use JavaScript libraries just to create visual effects that CSS can handle.

Existing functional libraries may be retained when replacing them is unrelated to the requested visual task, but never introduce a new external visual dependency.

---

## 4. Anti-Slop Gate

Before finalizing a design, check whether it contains generic AI UI patterns.

Reject or revise unnecessary use of:

- glassmorphism
- gradient backgrounds
- neon/glowing effects
- excessive rounded cards
- excessive pills
- giant hero sections
- repeated identical metric cards
- decorative blobs
- arbitrary shadows
- excessive icons
- decorative charts
- generic SaaS dashboard layouts
- excessive animations

The goal is not to make the UI unusual for its own sake.

The goal is to make it **intentional, restrained, recognizable, and useful**.

---

## 5. CSS First

When a visual requirement can be solved with CSS, solve it with CSS.

Prefer:

```text
CSS class + state class/attribute
```

over:

```text
inline style generated by JavaScript
```

JavaScript should primarily change state/content.

CSS should determine presentation.

Use CSS custom properties for recurring design values.

Do not introduce arbitrary one-off values when an existing token can be reused.

---

## 6. Typography First

Before adding visual decoration, improve:

1. typography
2. hierarchy
3. spacing
4. alignment
5. grouping

Only then consider additional visual treatment.

Financial numbers should be highly readable and use consistent numeric formatting/alignment.

---

## 7. Color Discipline

Use semantic design tokens.

Do not invent a new color for every page.

Income, expense, warning, focus, and neutral information must use consistent semantic roles.

Themes must preserve semantic meaning.

Do not hard-code theme-specific colors into components when a theme token exists.

---

## 8. Component Rules

### Cards

Use a card only when a surface boundary helps grouping or hierarchy.

Do not wrap every section in a card.

### Buttons

Use clear action hierarchy.

Do not make every action a bright primary button.

### Inputs

Prioritize speed and clarity, especially in transaction forms.

### Tables/lists

Prefer readable rows and alignment over turning every row into a card.

### Modals

Use only when the task benefits from focused interruption.

### Icons

Use only when they improve recognition. Never add an icon merely to fill empty space.

---

## 9. Transaction UI Priority

Transaction entry is a high-frequency workflow.

Optimize it for:

- fast input
- clear labels
- predictable focus
- obvious amount hierarchy
- quick category/wallet selection
- mobile usability
- minimal unnecessary decoration

Do not sacrifice transaction-entry speed for visual novelty.

---

## 10. Responsive Rules

Build responsive behavior into the component from the beginning.

Do not treat mobile as an afterthought.

Avoid horizontal scrolling unless the information genuinely requires it.

When a desktop grid cannot fit mobile, change the information structure rather than merely shrinking every element.

---

## 11. Motion Rules

Use motion sparingly.

Every animation should communicate one of:

- entering/leaving
- state change
- feedback
- focus

If an animation only makes the UI look more impressive, remove it.

Always respect `prefers-reduced-motion`.

---

## 12. Accessibility Gate

Before finalizing:

- keyboard focus is visible
- contrast is adequate
- controls have accessible names
- color is not the only status signal
- interactive targets are usable on touch screens
- disabled/error states are distinguishable

Do not hide important information behind hover-only interactions.

---

## 13. Full Redesign Mode

If the user explicitly asks to redesign the whole website:

1. Do not redesign one page in isolation and call it complete.
2. Establish/confirm the global design tokens first.
3. Redesign the application shell and navigation.
4. Redesign representative core components.
5. Apply the system consistently across pages.
6. Preserve all existing functionality and data behavior.
7. Do not rewrite business logic merely because the UI is being redesigned.
8. Keep CSS as the primary visual implementation.

The redesign should look like one product, not a collection of independently generated pages.

---

## 14. Full Redesign Order

When doing a complete redesign, work in this order:

1. global tokens
2. typography
3. page background/surfaces
4. app shell
5. desktop navigation
6. mobile navigation
7. buttons
8. inputs/selects
9. cards/panels where needed
10. lists/rows
11. modals/drawers
12. feedback states
13. transaction UI
14. dashboard
15. secondary pages
16. responsive refinement
17. accessibility refinement

Do not repeatedly reinvent the same component on each page.

---

## 15. Review Questions

Before finishing a UI task, ask internally:

1. Would this still look intentional without gradients?
2. Did I use a card because it helps grouping, or because AI dashboards usually use cards?
3. Did I add an icon because it improves recognition, or because the space looked empty?
4. Could this design work fully offline?
5. Did I introduce an unnecessary dependency?
6. Does the hierarchy make sense in grayscale?
7. Does the interface still feel like the same Money Management product?
8. Did I preserve existing behavior?
9. Did I change only what the request required?

If the answer exposes unnecessary decoration or duplication, simplify it.

---

## 16. Output Discipline

For a normal UI task:

- inspect targeted files
- implement directly when the request is clear
- run relevant checks
- summarize briefly

Do not produce a long design essay unless the user explicitly asks for design exploration or a full redesign plan.

For a full redesign, use `DESIGN.md` as the specification and keep implementation decisions consistent with it.
